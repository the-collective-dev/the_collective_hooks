Ship one cohesive change all the way to verified-in-production, the way we shipped assess Phase 4 (`collective_assess_live`, PR #298 → v2.380.0) — used as the worked example throughout. The value is the **rails**: TDD before code, structural review, the promote gate, and live verification. The loop is mechanical on purpose so your judgment goes to the hard parts (what to build, triaging review findings, recognizing a prod gap), not the choreography.

> This skill is The Collective's instantiation of the portable, tool-agnostic [`docs/playbooks/agent-sdlc-spec.md`](../../../docs/playbooks/agent-sdlc-spec.md) (the universal loop + STOP conditions + risk tiers + principles) — filled in with our tooling. To run this discipline in another project, instantiate that spec there (fill its slot table); don't copy this house-specific skill verbatim.

## STOP conditions (the autonomy boundary — non-negotiable)

Run the loop autonomously **except** when you hit one of these. Then STOP and ask the operator:

1. **Prod-infra mutation** — changing env vars / scaling / DNS / a Railway service config on a live service. (Phase 4 needed Temporal env on `collective-mcp` — that required explicit authorization; the classifier correctly blocked it on a generic "keep going".)
2. **Dual-use / live-security action against a real target** — running probes, load, or auth tests against a running instance. Build the capability behind a `consent:true` + SSRF/intensity gate; do not *fire* it at a target without the operator's go + a named target.
3. **Scope / strategy fork** — when the next step is a genuinely new investment (a new phase, a sibling tool, a rewrite-vs-fix call), not the obvious continuation. State your default and let the operator redirect.
4. **A finding in a mandatory-stop category — regardless of your confidence.** These triggers are *objective*, not self-assessed (don't rely on agent self-calibration — it's the thing models are worst at): **(a)** any finding tagged security / auth / access-control / data-integrity; **(b)** any finding in a PHI/PII path (any HIPAA-gated client repo); **(c)** any silent-swallow `catch` (`catch {}` / `.catch(() => {})` with no log or rethrow); **(d)** any disagreement between your disposition and an independent reviewer; **(e)** any blocking finding you genuinely can't resolve. Fix it or get explicit operator deferral — **never self-clear a category (a)–(d) finding on your own confidence.**

Everything else — pure-logic features, read-only work, behind-the-gate deploys — loops without a checkpoint.

**Continuation discipline (operator ruling 2026-08-27, R11 in PRD-005) — the inverse boundary: STOPPING is also bounded.** A session with a non-empty queue of decidable work never stops to report, await prompting, or hand back. Exactly three stopping states: **(a)** the queue is empty; **(b)** every remaining item is blocked on the reserved set (prices · scope · client sends · merges/promotes · rulings) or a named upstream act; **(c)** a cap/park/kill condition fires. There is no fourth state, and (b) is narrower than it looks: **blocked-on-reserved parks THAT lane, not the session — the project backlog (INBOX/READY) is the queue.** When a lane parks, pull the next backlog item by priority and keep building. Reporting is a byproduct emitted at a genuine boundary, never a reason to stop; a turn that ends with decidable items queued is a logged defect regardless of how good the report was. (Measured: three continuation prompts in one session — "keep going… I should not have to say this… I am headed to bed" — each one a minute the design failed to save.)

## The loop

0. **Orient — in the platform, not from memory.** `collective_where_am_i` (free) for the active objective, ready count and blockers, then `collective_set_objective` for what you are about to do. Commits auto-link to it, so a session with no objective produces commits that belong to nothing. **Measured 2026-08-26:** a full session ran with a stale objective from a previous session's work; nothing failed, which is exactly why it went unnoticed. `collective_project_status` additionally surfaces safety alarms (an expiring API key was found this way, one day out) and version/hook drift.

1. **Pick + scope.** One cohesive change — from `collective_whats_ready` (the queue is the product's own view of priority; picking outside it is a choice, not a default), the plan, a gap, or a found bug. If it's large or LLM-heavy, split (e.g. Phase 4 = pure `liveHarness.ts` core + the I/O tool, not one blob). Right-size the PR; isolate the risky/big part. **Classify the risk tier** (when unsure, round *up*): **T0** docs/comments/pure-refactor (full auto, TDD step N/A) · **T1** isolated pure-logic / read-only feature (full auto, standard loop) · **T2** service behavior / new write path / route / additive migration (full auto through the gate, exercise it at step 12) · **T3** auth / access-control / PHI-PII / money / data-integrity / destructive migration / infra / **any merge that itself deploys to production** → **mandatory STOP, human in the loop**, stage exposure before full prod when available. Higher tier → more rigor + earlier human checkpoint. T3 intersects STOP #1 (infra) and STOP #4 (security/PHI/data findings) by design.
1b. **Spec-shaped? Upload it BEFORE the code.** If the change introduces a data model, a contract, a new surface, or a decision someone will later need to cite: `collective_upload_spec` → wait → `collective_spec_review` → triage → `collective_review_decision`. CLAUDE.md has said "NEVER skip step 2" for a long time and it was still skipped, because CLAUDE.md is ambient and this loop is what gets executed step by step — so the step lives here now. **Measured 2026-08-25:** a contract data model shipped across four PRs without ever being uploaded as a spec or persona-reviewed; the reviews that did run were code reviews on the diffs, which cannot ask whether the model is right.

    **Review convergence is DELEGATED (operator ruling 2026-08-26, R10 in PRD-005):** run the review loop yourself — do not bring the operator per-round findings. **At most 5 rounds per spec; expect 2–3 to reach stable.** Stop when any of: (a) the review's label is acceptable/minor-gaps; (b) a round surfaces zero genuinely-new CRITICAL/HIGH classes (re-derivations of already-ruled decisions don't count — a reviewer will re-derive a near-constant cross-spec load every round against a growing sibling corpus; **class novelty, not finding count, is the convergence signal**); (c) plateau — the same finding classes reproduce with new wording. Grep-verify every code-citing claim before accepting it (reviewers confabulate files). Keep a convergence ledger in the spec (round → count → disposition). Findings that price, scope, or rule remain the operator's — park them as named rulings with your recommendation; never spend a round re-litigating one. **Measured 2026-08-26/27 across four specs and thirteen rounds: the 2–3-round expectation held on every spec** — the platform-rewrite round is the one big convergence step; after it, disposition by class.

2. **Isolate.** From the repo root (`REPO=$(git rev-parse --show-toplevel)`): `git worktree add "$REPO/../thecollective-<slug>" origin/main` → `ln -s "$REPO/backend/node_modules" "$REPO/../thecollective-<slug>/backend/node_modules"` → `git -C "$REPO/../thecollective-<slug>" checkout -b feat/<slug>`. **Always a worktree** — parallel Claude windows share the working dir and *will* collide (this session lost a branch to it). Never push `main`.
3. **TDD — failing test first.** Write the unit test on the **pure-logic core**, run it, watch it go red, *then* implement to green. Keep the bug-risk surface pure; I/O is thin glue around it. (Phase 4: `summarizeLoad`/`interpretLoad`/`safeLoadConfig`/`interpretIdor`/`isSafeLiveTarget` were pure + 15 tests; the `fetch` loops were ~20 lines of glue.) No "I'll backfill." **A behavior bug — even in I/O glue — ships with a regression test that fails before the fix** (extract/export the glue + drive it with a mock; the testing-policy "glue/rename" escape hatch does NOT cover behavior bugs). This run's load-probe rate bug proved it: a fake-fetch test asserting the per-second floor caught the class. **RED-PROOF is the hard gate: the regression test MUST fail against the pre-fix code — run it red before you implement; a test that passes pre-fix proves nothing.** Reproducing the production symptom in the red state (that retro: the backstop test failed by *hanging to timeout* — the literal prod symptom) is stronger when achievable but is **NOT required** — don't fabricate a weak symptom-repro to claim it.
4. **Verify locally.** `cd backend && npx tsc --noEmit` (exit 0) + `npx jest tests/unit/<area>` (all green).
5. **Bump via CHANGESET, not direct edit.** Drop ONE file at `backend/releases/next/<short-slug>.json` — `{ "summary": "fix(area): one line", "changes": ["detail"] }` — when you touch `mcp-server/**`, routes, or generators. Do NOT edit `backend/package.json` or `backend/releases.json` yourself: any two version-bumped PRs conflict by construction on those two files (measured 2026-08-13/14: four open PRs, every conflict was exactly those files and none was code), while separate files in a directory never collide. `apply-changesets.ts` folds them at release. Direct edit remains valid only for a one-off hotfix — and then **targeted text-insert at the top, NEVER reserialize the whole file** (`json.dump` / `jq -S` rewrites every entry → a thousands-line diff).
6. **Commit → push → PR.** Descriptive body, a `DISCIPLINE:` line on review-driven fixes, `Co-Authored-By`. `gh pr create`. **Then `collective_record_commit` for any commit that implements tracked deliverable work** — it records CODE_COMPLETE evidence and advances the matching acceptance criteria; it is idempotent per SHA and free. Skip it only for chores, merges and docs that deliver nothing trackable, and skipping is a judgment you make, not a default you drift into. **Measured 2026-08-25/26:** the PostToolUse hook asked for this after roughly eight commits in one session and was ignored every time — a nudge no step owns reads as decoration.
7. **Review — `collective_pr_review` with `includeMercury: true`.** NEVER the built-in `/review` skill. **Scale review BREADTH to risk, not the boundary** (a client engagement retro: 7 finder angles on a +33/−11 T2 diff — 3 returned empty, the reuse/simplification/efficiency angles produced pre-existing micro-noise; *all* the value came from one angle, altitude):
   - **Breadth by tier×size:** T0/T1 trivial → self-review only; T2 small (≲50 LOC, 1–2 files) → three lenses (line-scan · **altitude** · cross-file); T3 or multi-file → full panel + `crossVerify: true`. *(This split is a DEFAULT off one PR — the lens-hit log below is what calibrates it.)*
   - **Risk overlay is ADDITIVE (union, not escalate-to-full-panel):** when the diff touches a RARE high-stakes signal — **migrations / auth / access-control / money / payment / raw concurrency primitives (lock·mutex·semaphore)** — ADD `crossVerify: true` (the independent cross-vendor gpt-4.1 skeptic, builder-≠-reviewer per STOP #4(d), same primitive as assess Phase 3e) + the one lens matching that risk class. Do NOT drag the whole panel onto a small diff. Keep the signal list rare: a DB call / webhook / `await` is in nearly every diff and would re-inflate every review — NOT triggers. *(That bug was a DB call in a webhook; **altitude**, not a keyword, is what caught it.)*
   - **ALTITUDE IS MANDATORY ON EVERY BUGFIX / HARDENING PR (any tier):** "is this the instance or the class?" — does the fix cover the bug CLASS (the next sibling `await`/call/branch protected by default, e.g. an outer backstop) or just the lines someone flagged? That retro: the first cut wrapped exactly the two `await`s Mercury cited and one analog — answering the comments, not auditing the class; review found two more unguarded `await`s in the same handler → fixed with an outer backstop. A fix that patches cited lines but not the class **looks done** and is worse than one obviously unfinished.
   - Triage every finding: **Real** → fix it (TDD the new case). **False positive** → disregard *with a stated reason* (a `crossVerify` flag is *evidence*, not a substitute for your own check). **Blocking** → must fix before merge. Converged advisories (multiple reviewers + Mercury agree) are almost always real.
   - **LENS-HIT LOG — a required line in the PR body, not a good intention.** One line per run: which lens produced each outcome-changing finding, which returned empty. Put it in the PR description under `Lens hits:` so its absence is visible in the diff. **Measured 2026-08-25:** three reviews ran in one session and the log was skipped all three times without anyone noticing — a step that is easy to skip silently and produces no immediate feedback will keep being skipped, so it either becomes structural or it should be deleted rather than sit there being ignored. This is the data that calibrates the breadth table above; without it, the table never improves.
   - **Field data #2 (a day-one 4-PR set on a client engagement) — validates the table + the additive overlay:** the outcome-changing finding came from the MATCHING risk lens every time — concurrency lens on lock code → run-lock wired into only **1 of 3 crons** (instance-vs-class, same shape as that one); security lens on a `SECURITY DEFINER` migration → default PUBLIC EXECUTE grant; cross-file on a cron-auth diff → scheduler POSTs but route only exported GET — a prod bug in *adjacent unchanged code* (the "read the enclosing function + callers" rule paying for itself). Full 7-lens panel on the one T3 multi-file PR: 4 lenses carried all 8 confirmed findings, 3 produced noise — full panel stays correct for T3 multi-file; expect ~half the lenses to carry it. **Reviewer-side corollary (spec/persona reviews):** 3-bucket every finding set (genuine / refuted-with-a-stated-reason / already-tracked) and grep-verify every code-citing claim before accepting — the same session's 5 ADR reviews ran 53 findings at ~50% refutable, and the 2026-06-05 SPEC-092 review confabulated a `changeRiskClassifier.ts` that exists nowhere in the tree.
8. **Harden.** Apply the fixes, re-test, push, and note the hardening in the changelog entry. Re-run the review only if the change was substantial.
9. **CI to green.** Background-poll the PR's `Integration Verification` run to `success` before merging.
10. **Merge.** `gh pr merge <#> --squash --delete-branch` — only when CI is green **and** the promote gate is idle (a running gate will get cancelled by your push; rapid parallel merges cause cancellation churn). **Tier the ACTION, not just the change.** If merging to the target branch *itself* deploys to production, the merge IS a production deploy — that is **T3 infra → mandatory STOP**, regardless of how the diff tiers. Check before merging: does the target branch carry a `push:`-triggered deploy workflow, or a platform integration (Railway/Vercel/Fly) that ships on push? If yes, hand the merge to the operator. On 2026-08-13 this step was followed correctly on a T2 diff and shipped PR #972 to production unattended, because `promote.yml` carried `on: push: branches:[main]` and `main-protection` required 0 approvals — nothing malfunctioned; the tier taxonomy just never asked what the merge would *do*.
11. **Deploy via the gate.** The squash-merge to `main` auto-fires the SPEC-069 `promote.yml` gate (staging → smoke → prod → smoke). Do **not** push `main` directly. Background-monitor prod until the version flips. Railway's control plane flakes — the gate's widened retry (5×, ~300s) rides through most of it; if a gate run fails on `backboard.railway.com` it's infra, not you — re-trigger when it recovers.
12. **Verify live.** Confirm `curl …/health/live` + `/mcp-health` show the new version. For behavior changes, **actually exercise it end-to-end** — this is the step that matters most. (Running assess `runServerSide` for real is what exposed the `collective-mcp` ↔ Temporal prod bug that all 181 unit tests missed. Unit-green ≠ works-in-prod.) MCP-staleness caveat: your in-session MCP client won't see tools deployed *this* session (anthropics/claude-code#27142) — hit the deployed server's `/mcp` HTTP endpoint directly, or restart.
12b. **If verify-live fails — roll back, don't push forward.** Green-in-CI-but-wrong-in-prod is the dangerous case; the response is *structural*, not a judgment call: **(1)** restore service first — re-fire the gate to the last-SUCCESS version, or Railway dashboard → service → most recent SUCCESS → "Redeploy this version" (fastest); during an active outage use the CLAUDE.md Path A skip-staging gate. **(2)** confirm recovery — `curl https://api.thecollectiveai.dev/health/live` 200 on the prior version. **(3)** emit an incident artifact — `docs/postmortems/<date>-<name>.md` or a tracked status-report: what shipped, what verify-live caught, the rollback. **(4)** THEN diagnose on a *fresh* branch — never "re-fix in place" on main. **A failed verify-live is itself a STOP** — surface it to the operator before re-attempting. (Mechanism already exists — CLAUDE.md "Outage Response"; this just makes it the loop's *defined* failure path.)
13. **Capture — route it, and NAME the destination in the PR body.** "Write a memory" was the whole of this step for a long time, and the result was that every lane invented its own map: one lane used PRs-as-specs plus work items plus insights, another used GitHub issues plus memory and opened zero work items. Both defensible; the divergence is the defect, because "where is everything about X?" then depends on which lane you ask. Route by what the fact IS:

    | The fact | Home | Tool |
    |---|---|---|
    | Engineering truth — what to build and why | Spec in-repo via PR | `collective_upload_spec` (step 1b) |
    | Commercial truth — sold, classified, owed, receipted | Work item | `collective_todo_create` / `collective_complete_item` |
    | A finding someone else must own | Work item, + a GitHub issue in the platform repo for engineering detail | `collective_todo_create` |
    | A convention that must outlive any one document | Insight → CLAUDE.md, so it loads every session | `collective_add_insight` **then `collective_refresh_claude_md`** — the insight alone does not update the file, and an insight that never reaches CLAUDE.md is one no future session reads |
    | Operator-facing state that must survive compaction | Memory file | (memory) |
    | What the client agreed | The signed document / the thread | — |

    **A mandatory-stop-category finding that is PRE-EXISTING gets filed, not fixed in an unrelated PR** — the fix is someone's call, and burying it in a diff about something else removes their chance to make it. State the destinations in the PR body under `Captured:`; a capture step with no visible output is one that decays, which is precisely what happened.
14. **Clean up + loop.** `git worktree remove <wt> --force`; pick the next unit.

## Cross-cutting principles (apply at every step)

- **Verify, don't assume.** Read `SCHEMA-LIVE.md` (not `schema.prisma`) for DB truth; introspect before destructive SQL; `git branch --show-current` before committing after stash/checkout; re-grep doc claims against HEAD.
- **Enforce structurally, not by instruction.** Prefer a gate/hook/test that *can't* be skipped over a reminder. (Phase 4's anti-DoS is a hard `safeLoadConfig` clamp, not a "please don't flood" note.)
- **Report honestly.** Don't overclaim "done" — state what you verified, what you skipped and why, and what you *couldn't* do (e.g. the live e2e you can't run from a stale MCP session). Tests failing? Say so with the output.
- **Right-sized, isolated PRs.** One cohesive change; group only when genuinely cohesive; give the big/risky thing its own PR.
- **A ruling that contradicts shipped instruction text ships WITH the amendment.** When the operator rules something that conflicts with a skill, CLAUDE.md, or a runbook, the edit to that text is part of the work — not a follow-up. An unamended ruling has not landed: the next session reads the shipped text, not the comment thread, and the ruling silently loses. **Measured 2026-08-25:** the operator ruled that AI may propose pricing for their approval, while `c-sow-posture` still said *"Leave every price blank: no figure, no range, no qualitative sizing"* and `c-change-note` said the operator prices it. Amend so the guardrail MOVES rather than disappears — the original rule existed to stop a machine-set price reaching a client, so the amended form is "a figure may be proposed into an operator-facing surface; nothing priced reaches a client without recorded operator approval."
- **Before you CLAIM a gap, grep for the capability.** "Verify, don't assume" above covers claims about code; this covers claims about what the platform *cannot do* — and those are the ones that get reported upward as platform limitations and then designed around. Check the tool's own `inputSchema`, grep the routes for the verb and path, and read the enum before saying a field is unsupported. **Measured 2026-08-26, twice in one session:** a lane reported "milestone_create has no status parameter" when it accepts the full enum and documents its default; then, diagnosing that, this loop's own operator claimed milestone editing was impossible and built a duplicate `PATCH /milestone/:id` — the route had existed since 2026-05-13, and the duplicate would have silently shadowed it. **The cost of a false gap is a redundant build plus whatever it collides with**; the cost of checking is one grep.
- **Governance text is NOT T0.** A change to a skill, CLAUDE.md, a runbook or any instruction other sessions execute gets a review regardless of diff size. The tier taxonomy sizes the DIFF; it does not ask what the change GOVERNS — a twelve-line prose edit that changes what every future session does has a wider blast radius than most code. **Measured 2026-08-26:** this very amendment was self-cleared as "T0 docs, self-review only per the breadth table" — technically permitted, and an audit exempting itself from its own rule. The operator caught it; the review that followed found a real error in the new routing table. Same shape as "tier the ACTION, not just the change" at step 10, applied to instructions instead of deploys.
- **A skill that exists twice will diverge.** Before amending governance text, check whether the file exists in more than one place — a published/plugin copy and an internal copy are usually NOT the same file. **Measured 2026-08-25:** `c-ship` had forked; the published copy operators actually load was eleven days stale and missing a mandatory-STOP rule, while nine sibling skills were byte-identical. Writing an amendment into the wrong copy creates a third state. Generation from one source beats hand-syncing two.

## Worked example — assess Phase 4 (`collective_assess_live`, PR #298 → v2.380.0)
